01 / UNDERSTAND

Five ideas worth keeping.

An experiment needs a comparison contract.

Hold inputs or traffic assignment, time window, grading criteria, and success thresholds consistent. Change one variable at a time. If the model, prompt, and retrieval all change together, a new score does not tell you which component helped or hurt.

↗ Lesson 6:00

Start offline; confirm where the system will operate.

An offline golden set is a cheaper way to reject poor changes. A successful candidate still needs production confirmation on comparable traffic. Predeclare the evaluation window and avoid stopping at the first favorable fluctuation. No meaningful difference is a valid result.

↗ Lesson 9:00

Separate failure families before choosing a remedy.

Integration failures include missing data, tool errors, and post-processing. Prompt failures involve unclear or conflicting behavior. Hallucination involves unsupported claims. Model mismatch remains plausible when clean, sufficient context still exceeds the model’s ability.

↗ Lesson 16:00

Test the cheapest discriminating hypothesis first.

Quantify the symptom, list competing causes, inspect version differences and traces, and reproduce the suspected component in isolation. A bad answer after re-indexing should prompt a retrieval check; correct evidence that is ignored points toward prompt or use-of-context problems.

↗ Lesson 22:00

Target the weak slice and preserve reversibility.

If only a difficult class fails, evaluate selective routing or a better decomposition rather than upgrading every request. After a fix passes the original metric, expand traffic gradually while monitoring regressions and retaining the baseline for rollback.

↗ Lesson 37:00

Diagnose before optimizing

  1. Quantify the symptom
  2. List competing hypotheses
  3. Collect the cheapest decisive evidence
  4. Reproduce one cause
  5. Fix and rerun the same metric
  6. Roll out gradually with rollback

DETAIL 01

Freeze the components outside the experiment

The deck identifies six things that can be tested: prompt version, examples, retrieval strategy, chunking, model/effort, and validation. For an interpretable first experiment, vary one and pin the rest. Declare metrics, slice limits, effect size, and stopping criteria before seeing results. Use comparable traffic and time windows; a temporary lead is not a reason to stop.

DETAIL 02

Attach evidence to each failure hypothesis

The four families guide investigation; they are not mutually exclusive or exhaustive diagnoses. Define a numerical symptom, inspect the least expensive discriminating evidence, isolate the suspected change, and rerun the original metric after the fix. A model change remains a hypothesis when prompt and evidence checks do not explain the failure.

HypothesisUseful evidence
Prompt failureDiff against the last-good instructions; inspect ignored context
Integration failureRetrieved IDs, index version, tool outcomes, malformed input
Unsupported claimsClaim-to-source checks on the frozen evaluation set
Capability mismatchRepeated failure on hard cases with manually verified context

DETAIL 03

Interpret the isolation grid carefully

In the coding-assistant scenario, acceptance falls from an illustrative 34% to 27% while the model, prompt, and chunker all change. New-model/old-prompt/old-chunks and new-model/new-prompt/old-chunks comparisons recover the baseline; old-model/old-prompt/new-chunks fails. That implicates chunking in the example. It does not rule out every interaction, so confirm the repaired configuration as a whole.

Illustrative comparisons
New model + old prompt + old chunks → baseline recovered
New model + new prompt + old chunks → baseline recovered
Old model + old prompt + new chunks → regression persists

Repair the chunker → rerun → expand traffic with rollback gates.

DETAIL 04

Do not let an aggregate hide the hard slice

Another scenario reports 91% overall accuracy while the hardest tenth of requests achieves only 58%. With a firm cost ceiling and latency headroom, test targeted routing or decomposition for that class rather than upgrading every request. The migration example instead points to superseded-policy metadata: verify version/date filtering and index updates before adding a larger model.
