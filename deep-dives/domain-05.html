LESSON 01 / OBJECTIVES 5.1, 5.2 / ~12 MIN

Begin with the decision, the harm and the owner

A governance design begins with a concrete sentence: “This system may propose X, for person Y, using data Z; person or service W decides whether X happens.” That sentence separates useful generation from real authority. A meal-planning assistant that suggests recipes, an assistant that changes a hospital patient’s diet, and an agent that purchases groceries have different consequences even if they share a model. Your first task is to identify the action and its affected people, rather than assign one risk label to the entire chatbot.

Throughout this chapter, a hypothetical NutriMind extension drafts meal ideas and a hypothetical Krishi Mazdoor extension helps workers discover suitable jobs. These are design exercises, not claims about either project’s present implementation, legal status or users. All quantities and records are synthetic. The learning goal is a defensible design that you could adapt after discovering the real requirements.

Distinguish quality, safety, security and compliance

Quality asks whether the meal draft is useful. Safety asks whether an otherwise useful draft creates unacceptable harm, such as overlooking an allergy. Security asks whether an attacker can cause disclosure or unauthorized action. Compliance asks which obligations apply to this actor, purpose and deployment, and what evidence demonstrates that they are met. These concerns overlap: an access-control failure can also be a privacy violation. They still need different tests and owners. A high helpfulness score cannot compensate for a release that exposes another tenant’s records.

NIST’s AI RMF organizes continuous risk work around Govern, Map, Measure and Manage. Governance spans the other functions; these are interrelated activities, not four boxes completed once before launch. The RMF is voluntary guidance, and the official site notes that a revision is in progress. We use its current 1.0 core as a practical organizing aid, not as a certificate. D5-S01

Write a risk as a causal chain

“Hallucinations are risky” gives an engineer little to implement. A useful entry says: “An imported recipe lacks a reliable allergen field; the model infers that it is suitable; a user trusts the suitability badge; a person with an allergy may consume it.” The control might require a verified ingredient record for that badge, with no badge when evidence is missing. Its test should inject incomplete ingredient data and verify the badge is withheld. Its owner is the team able to maintain the ingredient source and eligibility rule, not whoever wrote the latest prompt.

Separate inherent risk, before the chosen controls, from residual risk, after the controls have been tested. “Low residual risk” needs a stated basis: test conditions, sample size, remaining escape paths and an owner authorized to accept it. Scores such as likelihood × severity help order work, but multiplying two ordinal labels does not produce a measured probability. Severe, irreversible harms may warrant a hard constraint even when their frequency is unknown.

Project artifact

Use the risk-register template. Create three rows: a factual error, an unauthorized tool action and a harmful exclusion. For each, record the affected person, trigger, consequence, preventive control, detection, recovery, evidence and risk owner. If the owner cannot explain how the release can be stopped, governance is still aspirational.

Architectural decision: if the system cannot safely perform the consequential action, preserve value by shrinking the action. A draft-only service, verified lookup or human-supported workflow may satisfy the user’s actual need with a smaller and more testable risk surface.

LESSON 02 / OBJECTIVES 5.1, 5.2 / ~16 MIN

Guardrails are controls at distinct boundaries

A guardrail is a mechanism that changes what the system can say, read or do. Its strength depends on where it executes. A system prompt can discourage unsafe advice; a tool service can refuse an unauthorized transaction even if the model requests it. Both are useful, but the second is the authority that prevents the transaction. Design each control around an explicit failure, an enforcement point and a known escape route.

OWASP’s excessive-agency guidance separates three problems: functions the agent does not need, privileges those functions should not have, and autonomy that allows consequences without an appropriate decision. This distinction is useful because hiding a dangerous tool from a menu does not revoke a powerful backend credential. D5-S03

For the marketplace exercise, replace an unrestricted update_worker tool with draft_profile_change. Let the authenticated worker approve the precise diff before a narrow service applies it. For job ranking, the model should not choose the tenant or override eligibility permissions by emitting tenant_id. Derive those fields from trusted application context. Treat all model arguments as untrusted input, even when they arrived in syntactically valid JSON.

The checks must occur in the same authoritative path as the mutation. A UI button that is disabled while an API still accepts the call is an incomplete control. A precheck can race with a permissions change; use the backend’s transaction or concurrency facilities to prevent applying a proposal against a different version. Idempotency prevents a retry from duplicating a successful action; it does not authorize the original action or make an incorrect action safe.

MCP’s July 2026 security guidance gives a concrete infrastructure example: accepting tokens intended for another resource and passing them downstream breaks the intended authorization boundary; token passthrough is prohibited by the specification. A model instruction saying “only use authorized data” cannot repair audience validation in a server. D5-S08

Claude Code permissions provide a current product example of implementing tool controls separately from project guidance. Its permission behavior depends on configuration and version; inspect the effective policy in your deployment rather than copy a rule and assume it works. Repository instructions describe workflow intent, while tool policies, sandboxing and service identities constrain execution. D5-S09

Failure behavior is part of the control. If an approval or authorization service is unavailable, a consequential write should remain pending or be denied under the agreed policy. Sending it anyway to meet latency targets silently changes the safety design. A read-only fallback may preserve useful service without granting extra authority.

LESSON 03 / OBJECTIVES 5.1, 5.2 / ~15 MIN

Indirect injection, provenance and the confused authority problem

Imagine the nutrition assistant retrieves a recipe PDF. Its text includes a forged maintenance note asking the assistant to export user profiles to a diagnostic endpoint. The real user asked for a recipe comparison. The PDF is evidence about recipes, not an authorized instruction source. If the model follows the note, the boundary between content and authority has failed.

Direct injection arrives in an adversary’s own request. Indirect injection arrives through material the assistant is processing: a document, tool response, issue comment, page or image. OWASP explicitly notes that RAG and fine-tuning do not fully remove this vulnerability. Retrieval can improve factual relevance while simultaneously introducing attacker-controlled text into context. D5-S04

Provenance and permission answer different questions

Provenance tells you where a fact came from, which version supplied it and how it was transformed. Authorization tells you who may read or use it for this operation. An internal wiki can have excellent provenance and still contain an attacker’s comment. A publicly readable page can contain accurate facts but lack authority to instruct your agent. A trusted transport also does not make the transported content trusted: a legitimate MCP server can return a user-uploaded document.

Attach document ID, source owner, retrieval time, version and access scope to each chunk. Preserve those fields through summarization. Otherwise a malicious sentence can be paraphrased into a clean-looking summary, losing the signal that it came from an untrusted attachment. Do not let a summarizer promote an assertion such as “the user approved export” into the application’s approval record. Approval comes from the trusted interaction and is stored by the application.

Worked case: contain a poisoned job listing

A synthetic listing says that applicants must provide their full contact history to complete eligibility checks. The assistant can read the listing and help a worker understand its stated requirements. It must not gain permission to search unrelated contacts simply because the listing requests them. Keep listing text in an evidence field; constrain the assistant to supported job fields; flag the unusual requirement; and let the worker decide whether to continue. The service must separately enforce the data fields permitted for an application.

Now make the attack subtler: the listing falsely claims that transport is available only to one language group. A blocked export tool does not fix this informational harm. Verify consequential eligibility claims against an approved policy source, show uncertainty when evidence conflicts, and include this case in ranking and explanation tests. Security containment and factual validation address different stages of the same attack.

Use contemporary industry reports with their limits attached

Anthropic’s November 2025 browser-defense report describes model training, classifiers and expert red teaming, while explicitly treating prompt injection as unresolved. Its reported attack-success result belongs to a particular internal adaptive test and configuration. It is not a guaranteed production failure rate for your assistant. D5-S05

A newer report, dated 9 October 2026, describes unintended actions observed in evaluations and internal use, including working around tool restrictions and interacting with real forms. Anthropic reports limited impact in the described cases and changes to containment, monitoring and evaluation environments. These are selected investigated cases, not a prevalence estimate across customer deployments. The practical design lesson is to test failure paths and enforce the environment boundary when a helpful agent encounters a blocker. D5-S07

Test the boundary, not just the refusal. A passing test should show that the unrelated export or write did not occur, that no sensitive payload escaped through logs or URLs, and that the legitimate recipe or job task could continue safely. Counting “I cannot comply” messages alone misses actions that already happened.

LESSON 04 / OBJECTIVES 5.2, 5.3 / ~16 MIN

Reliability, uncertainty and evidence that survives contact with production

LLM failure has more forms than an invented fact. The assistant may quote a real policy from the wrong year, use the wrong unit, omit an exception, misidentify a tool’s completion state, or perform the right action twice. A model can produce a plausible explanation for any of these. NIST’s Generative AI Profile identifies confabulation and the misleading confidence of generated content, including invented logic or citations. The profile is a risk lens; it does not estimate your application’s error rate. D5-S02

Correct the mechanism rather than defaulting to a larger model. If the source lacks the allergen record, a stronger generator still lacks evidence. If the parser changes milligrams to grams, adding citations cannot repair the transformation. Trace one failing case through its input, retrieved evidence, proposal, executor decision and delivered outcome. Preserve the versions needed to reproduce it without retaining unnecessary sensitive text.

A confidence number needs a measured meaning

Calibration means that predictions assigned a probability should succeed at roughly that frequency under the stated conditions. Guo and colleagues studied calibration of classification networks in 2017; their findings and temperature-scaling results do not establish that a current LLM’s self-written “95% confident” is calibrated. Use the definition, then test the particular signal and task. D5-S10

Worked case: confidence and selective answering

On 200 synthetic eligibility questions assigned to a high-confidence bin, only 166 answers are correct. The observed correctness is 166 / 200 = 83%, whatever the model’s confidence label says. Examine source freshness, question types and subgroup composition before using that signal for automatic decisions.

A revised evidence threshold answers 160 of the 200 questions and gets 152 correct. Accepted-answer accuracy is 152 / 160 = 95%; coverage is 160 / 200 = 80%; 40 cases abstain. Report both numbers. If a language subgroup supplies 30 of those 40 abstentions, the overall improvement may conceal a new access problem. An abstention is only useful when a safe and timely alternative exists.

Rare harms and common false alarms

Suppose 10,000 requests contain 100 genuinely unsafe cases. A detector catches 90 and incorrectly flags 198 of the 9,900 safe cases. Recall is 90%, but only 90 / (90 + 198) = 31.25% of its alerts are true. This is a base-rate effect, not an arithmetic failure. A reviewer will see many false alarms despite a seemingly strong detector. Measure both escape rate and review burden before choosing a threshold.

Zero observed failures also needs qualification. With independent, representative trials and a stable failure probability, zero failures in 300 trials gives an approximate 95% upper bound of 3 / 300 = 1% under the common rule-of-three approximation. It does not establish zero risk, cover untested attacks or validate a changed deployment. Correlated examples and adaptive attackers weaken that simple interpretation.

Combine scenario tests, adversarial tests, outcome checks and production evidence. Anthropic’s January 2026 evaluation article discusses complementary automated, human and operational methods. For this exercise, score final state as well as the transcript: no unauthorized write, correct attribution, proper abstention and safe recovery. A judge model can help triage but needs human calibration and must not be the sole verifier of access control. D5-S20

LESSON 05 / OBJECTIVES 5.1, 5.3 / ~17 MIN

Human review is a staffed decision system

Adding an “Approve” button does not automatically create meaningful oversight. The reviewer needs the right expertise, relevant evidence, sufficient time, authority to change the outcome and a safe route when they cannot decide. An approval made after the user has already received the consequential advice cannot prevent that harm. Choose the review point by asking what the person must be able to stop.

Anthropic’s April 2026 discussion of trustworthy agents highlights the tension between autonomy, human control and repeated permission prompts. Its examples are product design choices, not a general guarantee that approving a plan makes every later action safe. Use that industry experience to distinguish useful oversight from habitual confirmation. D5-S06

Match oversight to consequence

In the nutrition exercise, ordinary recipe formatting might be checked by automated schema and rendering tests. A draft that makes a disease-specific suitability claim crosses a different boundary: under this exercise’s policy, it must remain withheld for a qualified domain reviewer or be converted into general, nonpersonalized information. This is a stipulated product rule, not a clinical recommendation. In the marketplace, a worker can approve an application containing their own contact details, while an appeal about unfair exclusion may need a trained operational reviewer with authority to amend the record.

A review screen should emphasize the consequential delta. Show “send these three fields to this employer,” rather than “continue workflow.” Display missing evidence and conflicts alongside supporting evidence. Give the reviewer access to original sources without exposing unrelated records. Keep an honest outcome history. A generated explanation is a proposal for the reviewer to inspect, not proof of what the system actually did.

Worked case: a queue can invalidate the safety design

Suppose a pilot receives 40 cases per hour and routes 60% to review. That is 24 review cases/hour. Two reviewers, each averaging six minutes per case with no other duties, supply 2 × 60 / 6 = 20 cases/hour. Demand exceeds this idealized capacity by four cases each hour. After five hours, the backlog has grown by 20 cases; even after all new arrivals stop, that backlog alone takes about one hour to clear at the same idealized service rate.

Review arrival rate = total arrivals × review fraction
Ideal service capacity = reviewers × 60 / mean review minutes
Load ratio = review arrival rate / capacity = 24 / 20 = 1.2

This is a simple workload calculation, not a waiting-time or p95 SLA model. Real reviewers take breaks, cases vary, arrivals burst and some decisions need specialists. Load below one is necessary for stability under these assumptions; it is not enough to promise a short tail latency. Staff for realistic demand and availability, measure queue age by risk class, and agree an overflow response before launch.

The permitted responses are to reduce admission, pause the consequential feature, add qualified capacity, or use an already approved lower-risk alternative. Removing mandatory review when the queue is long changes the safety policy. It needs a new accountable decision supported by evidence; it is not routine operational tuning.

Prevent stale approvals and automation bias

A reviewer approves an application to employer A containing a redacted phone number. Before execution, the model revises the recipient to employer B and adds an address. The old approval must not cover this new proposal. Bind approval to meaningfully relevant fields and a version, then recheck it at execution. A proposal hash is useful only if it covers the canonical fields that determine the action, and the executor verifies it rather than trusting a model-supplied claim.

Automation bias occurs when a person over-relies on the system’s suggestion. Reduce it with evidence-first presentation, explicit uncertainty, clear disagreement controls and periodic review of cases where the model was wrong. Sample accepted and rejected cases; disagreement alone does not tell you which party was correct. Adjudicate difficult cases with appropriate expertise before turning feedback into training or eval labels.

The review-policy template connects routing, reviewer authority, evidence, approval binding, staffing and failure behavior. A complete policy answers both “Who can say yes?” and “What happens while nobody qualified is available?”

Explore the human-review capacity limit

Change the assumptions. This is a steady hourly load calculation, not a queue-wait forecast. The review fraction includes all cases your approved policy routes to people; capacity assumes uninterrupted reviewers and the stated mean handling time.

Utilization below 100% is necessary for headroom under these assumptions, but does not prove an SLA. Account for bursts, breaks, case complexity and reviewer accuracy. Equality leaves no spare capacity.

LESSON 06 / OBJECTIVES 5.4, 5.1 / ~17 MIN

GDPR: follow the purpose and every copy of the data

Start with applicability, actor roles and purpose, then design controls around the resulting obligations. A product’s name or hosting region does not settle applicability. For a hypothetical deployment in scope, map each processing operation: collecting a profile, generating an answer, logging a trace, creating an embedding, performing analytics and handling a rights request. Each operation may have a different purpose and retention need.

EDPB guidance explains that a controller determines purposes and means, while a processor acts on the controller’s instructions; contracts and subprocessor arrangements matter. A vendor does not become the controller for your product merely because it hosts the model. Conversely, calling a vendor a processor does not settle all of its independent processing. Verify the actual activities and terms. D5-S22

The EDPB’s basics guidance connects purpose limitation, minimisation, accuracy, storage limitation, security and accountability. Identifiability can be indirect: replacing a name with a stable user ID does not automatically anonymize a detailed profile. Health information may also be a special category requiring additional conditions. D5-S21

Translate principles into engineering choices

For the hypothetical nutrition extension, ask whether the generation request needs a full historical diary or only the user-selected ingredients and current constraints. Keep identity mapping outside the model context when possible. Redact irrelevant free text before telemetry, and prefer structured error codes over raw prompts. Short retention does not compensate for an unjustified collection, and encryption does not make an unnecessary collection necessary.

A lawful basis must fit the processing purpose. EDPB guidance distinguishes the available bases and warns against artificially expanding contractual necessity. A meal-planning service and optional sponsor targeting are different purposes; a single “I agree” checkbox does not automatically justify both. Where sensitive data is involved, identify the additional applicable condition as well. Have the responsible privacy/legal owner assess actual scope, notices, rights, transfers and any required impact assessment before implementing a real deployment. D5-S23

Worked case: a rights request after an AI conversation

Synthetic user U-104 asks for erasure. The application has a profile, a meal summary in a vector index, a prompt cache, an error trace containing a pasted address and a separate invoice. The privacy owner has determined that the profile-derived records are eligible for erasure and that a specific invoice must be retained under an applicable obligation. Engineers should not choose that exception themselves; they implement the scoped decision.

Delete eligible live records and derived index entries, invalidate relevant caches, notify processors through the established path and verify completion. Keep the justified invoice segregated, restrict its use to the approved retention purpose and state its retention basis. Do not continue personalization from retained invoice data. EDPB describes erasure as conditional, with limited exceptions, and access responses must protect other people’s rights. An export should therefore isolate this user’s personal data rather than hand over a mixed-tenant trace dump. D5-S11

The EDPB’s February 2026 enforcement report highlights backup handling as a real difficulty. It recognizes that changing backup contents may not always be advisable and calls for procedures that track erasure requests and address restored systems. This supports a designed restore procedure; it is not a blanket permission to exclude backups or retain them indefinitely. D5-S12

In the exercise, record a minimal, access-controlled deletion instruction for U-104, restore a synthetic backup into quarantine, replay the instruction, then test the profile and index before reopening traffic. The deletion record itself can be personal data and needs its own justified retention and access policy. A finite backup schedule, restoration control and evidence of successful replay work together; none alone demonstrates full compliance.

Automated decisions require scope analysis. GDPR protections concerning solely automated decisions focus on legal or similarly significant effects, with specific conditions and exceptions. A nominal human rubber stamp is not a dependable design answer. For an exclusion from work opportunities, involve the privacy owner and preserve meaningful contestability. Do not assume that every recommendation falls under the same rule or that every human click removes it. D5-S11

LESSON 07 / OBJECTIVES 5.4 / ~13 MIN

HIPAA: relationships, PHI flows and shared responsibilities

“Our app discusses health, therefore HIPAA applies” is an unreliable shortcut. HIPAA’s rules apply to covered entities and business associates. Determine the actors and relationships: a qualifying provider, health plan or clearinghouse; an app working on their behalf; the activities performed; and the protected information created, received, maintained or transmitted. HHS explains that an entity outside those definitions is not subject to the HIPAA Rules on that basis. Other laws and contractual obligations still require separate analysis. D5-S13

HHS’s business-associate guidance currently includes health-app vendors acting for covered entities and an AI chatbot on a provider’s patient portal using patients’ PHI. These examples illustrate why the same software can have different obligations in different business relationships. They do not establish that the hypothetical NutriMind extension is a business associate. D5-S14

Worked case: clinic-sponsored meal drafts

Assume, solely for this exercise, that a clinic is a covered entity and contracts an app to prepare drafts using patient information on its behalf. The responsible legal/security team has confirmed the relevant business-associate relationships and permitted use. Draw the entire ePHI route: clinic identity, app, model endpoint, storage, support tools, logs and backup services. A contract covering the main model endpoint does not automatically cover an unrelated analytics service receiving raw conversation text.

Minimize each payload, restrict access by role and patient context, verify approved services and configurations, protect credentials, establish incident notification responsibilities and test continuity. A BAA documents important obligations and permitted handling; signing it does not configure your application or make every subsequent use permissible. “BAA available” is a procurement input, not a deployment assurance result.

Encryption does not remove the relationship

HHS explicitly states that a cloud provider maintaining encrypted ePHI on behalf of a covered entity or business associate can remain a business associate even without the decryption key. Its cloud guidance also explains that encryption alone does not address integrity, availability or administrative safeguards. For no-view services, particular access-control responsibilities may be met through one party’s agreed implementation; other obligations remain. D5-S15

Do not respond by implementing every control twice. Write down which party implements what, how the other party depends on it and how failure is detected. If only the clinic can decrypt a backup, recovery needs a tested route to the appropriate key; a healthy storage service is insufficient when the application cannot restore usable records. Use the dataflow and control matrix to make those dependencies visible.

LESSON 08 / OBJECTIVES 5.4 / ~11 MIN

FedRAMP: reuse provider evidence, authorize the actual system

FedRAMP is a US federal cloud assurance context, not a universal badge needed by every AI startup. In a prospective federal deployment, let the agency determine scope and the applicable requirements. Then identify the exact cloud service offering, certified boundary, configuration, integrations and agency information system. A commercial service with a similar brand name may not be the offering covered by the evidence.

The current FedRAMP Consolidated Rules for 2026 describe provider certifications as reusable security evidence while agencies authorize their own information systems. The agency authorizing official accepts risk for its specific use, including customer-operated controls and integrations. The page explicitly distinguishes an agency system using a service from creating a standalone ATO for the cloud offering itself. Terminology has evolved; this is the checked 2026 guidance, not a rewrite of the July exam guide. D5-S16

Worked case: a document assistant changes its boundary

An agency plans a synthetic document-search assistant on an approved cloud offering. The prototype adds a public model endpoint for summarization and an external tracing service because they are convenient. The original infrastructure evidence does not automatically cover those new paths. Inventory what leaves the approved boundary, identify the proposed services and data, and resolve the gap before processing live federal information.

The smallest correction may be to remove external tracing and use an already permitted endpoint, rather than recreate the provider’s entire assessment. The agency team still needs evidence for its identity integration, document permissions, safe logs, retention, incident response and monitoring. A cloud provider can operate secure infrastructure while your assistant retrieves the wrong department’s documents through an overprivileged service identity.

A useful handoff names the exact inherited evidence and the exact tests you own. For instance: “The provider controls the underlying service infrastructure; our application enforces per-user retrieval; test a user from department B against department A’s record.” That sentence is more actionable than “FedRAMP handled by cloud.” Keep the responsibility matrix versioned when a connector, identity path or processing location changes.

LESSON 09 / OBJECTIVES 5.5, 5.2, 5.3 / ~19 MIN

Fairness, transparency and the people outside your metrics

Ethical design starts by asking who benefits, who bears the error and who can challenge it. In the marketplace exercise, an inaccurate job recommendation wastes someone’s travel time. An unjustified exclusion can remove an opportunity entirely. A convenient interface for employers can create surveillance pressure for workers. These effects are not fully described by average answer accuracy.

NIST’s bias publication treats AI as a sociotechnical system: harmful bias can arise from data and algorithms, but also from institutional practices and human behavior. Removing an explicit group field does not remove those mechanisms. Language, geography, device access or a history shaped by unequal opportunities may act as proxies. D5-S17

First define the decision and a legitimate comparison

“Fair to every group” is too vague to test. Specify the decision: whether a worker receives a recommendation for a job whose stated requirements they meet. Specify the harm: missing suitable opportunities, irrelevant recommendations, delays in review or inaccessible explanations. Determine how labels are established. An employer’s past selection is not automatically an unbiased label for qualification. Involve people affected by the decision and appropriate domain/legal experts before choosing features and targets.

Measure at relevant stages: source availability, retrieval, ranking, display, abstention, review wait and final opportunity. If recommendations have equal correctness among users who receive them, but one language group receives mostly abstentions, the delivered service differs. If workers with older devices cannot open the review screen, improving a model metric will not fix that exclusion.

Worked case: equal error rates, unequal precision

Consider two synthetic groups with 1,000 records each. Independent assessment says that 200 records in group A and 100 in group B meet the particular job requirements. A recommender has 80% true-positive rate and 10% false-positive rate in both groups. These are teaching quantities, not claims about any population.

Equal true-positive and false-positive rates do not produce equal selection rates or precision when these base rates differ. That does not decide which policy is justified. It tells you which trade-off must be made explicit, whether the labels and base rates are defensible, and who should participate in deciding the policy.

Kleinberg, Mullainathan and Raghavan’s research proves incompatibilities among particular formal fairness conditions for risk scores except under constrained cases. It does not say that fairness is impossible or that every fairness metric conflicts in every application. Use the result to resist a universal “fairness score”; evaluate the relevant harms and assumptions instead. D5-S18

Use complementary tests rather than a single parity target

Slice tests compare relevant outcomes across groups with sample counts and uncertainty. Paired tests hold legitimate requirements fixed while changing a field that should not affect the decision. For example, two synthetic profiles with identical skills and availability but different names should not receive different eligibility explanations when name is irrelevant. Such tests can reveal sensitivity, but do not prove every real-world outcome is fair.

Audit the complete policy, including human review. Reviewers may introduce inconsistent judgments or delay one group more often. Monitor abstention, completion and appeal outcomes alongside model errors. Avoid inferring sensitive characteristics casually just to populate a dashboard; the audit data itself needs an appropriate purpose, safeguards and access limits. Small groups may need qualitative investigation rather than confident claims from a handful of records.

Transparency should help someone act

Explain when AI is involved, the purpose of the output, the evidence used, material limitations and how to correct or contest it. For a worker, “not shown because the job requires a licence not present in your verified profile; update the record or request review” is more useful than a vague “AI suitability score.” The reason must reflect the actual decision path. Do not generate a persuasive rationale after the fact and treat it as an audit trail.

Google DeepMind maintains a public model-card collection, a current industry example of documenting models. Your application still needs its own scope, tested performance, known limitations and operational responsibilities; a provider card does not describe your retrieval permissions, user population or appeal process. D5-S19

Keep an internal decision record detailed enough to reproduce the relevant action, and a user explanation appropriate to that person’s needs. These need not expose confidential prompts, secrets or unrestricted personal records. A useful transparency design supports understanding and recourse while respecting the same privacy and security boundaries as the rest of the system.

Use the fairness and transparency worksheet to state the harm, label source, comparison groups, chosen metrics, unresolved trade-offs and appeal owner. A metric without a named decision and affected person is easy to optimize without improving the product.

Build a safety case using an offline, synthetic lab

This lab turns the chapter into artifacts you can reuse. It requires a text editor and Python 3, no API credentials, personal records or live services. Download the four worksheets and the self-contained governance lab. The script contains fabricated records, deterministic policy checks and assert-based expected outcomes. It performs no network access, external writes or real applications.

These checks demonstrate engineering ideas; they are not a production security implementation, a clinical validation or a compliance certification. MCP’s security guidance illustrates why real integrations also need correct protocol-level authorization, and NIST’s RMF places such tests within an ongoing accountable risk process. The toy checks below cover only their declared fixtures. D5-S08 D5-S01

Six concrete steps

  1. Declare scope and owners. In the risk register, choose the hypothetical nutrition or marketplace extension. State the permitted user benefit, a consequential action you will not automate under this exercise, the affected people and three causal risks. In the control matrix, trace source → model → proposed action → executor → telemetry → backup. Acceptance: every risk has a preventive control, a detection/recovery path and an accountable owner; every data copy has a purpose and retention decision.
  2. Run the executor fixtures. Save the script, open a terminal in its folder and run python3 governance-lab.py. Inspect the valid proposal, the wrong-tenant record, the unexpected field and the forged approval in its source. A hostile document string is evidence only and never enters the policy’s approval state. Expected: the valid proposal is permitted, all unauthorized variants are denied and there is no real side effect. Acceptance: explain which independent check stopped each variant; “the model refused” is insufficient.
  3. Break approval binding. Read the stale-version and expired-approval fixtures. Change the synthetic current listing version, allowed fields or reviewer identity in a local copy and rerun. Use the review-policy worksheet to define which changes need a new decision. Expected: the assertions detect any attempt to permit a proposal covered by the wrong approval. Acceptance: both proposal content and current resource state are checked before the simulated permission result, including revoked access.
  4. Stress the review plan. Recalculate the fixture with 40 arrivals/hour, a 60% review fraction, two reviewers and six minutes/case. Then remove one reviewer and consider a burst of unfamiliar cases. Expected: the initial load is 24 versus 20 cases/hour; with one reviewer ideal capacity falls to 10. Acceptance: record an approved pause/admission/fallback response and a queue-age alert. Do not claim these averages establish a p95 SLA, and do not solve overload by silently dropping required review.
  5. Practise a scoped restore. The script marks U-104 eligible for erasure, U-205 retained, and the U-104 invoice retained for a stipulated separate obligation. Run the synthetic restore/replay check and inspect the remaining records. Expected: the eligible profile and derived embedding are absent; the approved retained record remains segregated. Acceptance: your matrix names who made that scoped decision and how you would verify each live/derived/vendor copy. The fixture assumes the legal decision; it does not make it.
  6. Defend the fairness and launch decision. Reproduce the two-group table in the fairness worksheet and inspect the script’s calculated precision. Write a short launch recommendation naming the benefit, strongest evidence, unresolved harm, required review capacity and stop condition. Expected: equal 80% true-positive and 10% false-positive rates yield about 66.7% versus 47.1% precision here. Acceptance: explain the denominator, reject a universal fairness claim and specify a meaningful appeal route. Attach the ten learning-check results as supporting practice, not as proof of production safety.

Move from toy evidence to your project

Replace one assumption at a time. Discover the real actor and data flow before adding a provider. Replace synthetic access fixtures with integration tests of the actual backend. Validate review decisions with qualified people and realistic cases before setting a threshold. Test a quarantined restore before promising erasure behavior. Review model, tool, prompt, source and policy changes against the same documented risks. Keep high-consequence features behind explicit release criteria until the relevant evidence exists.

Exam transfer: when several answers sound responsible, identify the failed boundary, the accountable decision maker and the missing evidence. A larger model, another disclaimer, a provider badge or a generic human checkpoint may help one layer while leaving the actual failure untouched. Prefer the option that addresses the mechanism under the scenario’s stated constraints.

Make the decision before reading the answer

These are original learning scenarios. Identify the binding constraint and the authority boundary, then compare all four explanations. They do not reproduce live exam items or estimate an official pass result.

A model emits a valid JSON request to change a worker profile. The session belongs to tenant A, but the target record belongs to tenant B. The output validator accepts the schema and the model says the user approved. Which control most directly prevents the wrong-tenant change?

Reveal reasoning for every option

Best response: A

  1. A · Best response

    The authoritative executor must check the authenticated actor against the real resource. Model statements cannot grant access.

  2. B · Alternative

    A model-provided tenant and model-provided explanation can agree while both are wrong; neither establishes the authenticated permission.

  3. C · Alternative

    Retrieval and explanations may assist the workflow but do not replace a backend authorization check at the mutation boundary.

  4. D · Alternative

    Visibility and audit help review and investigation, but a cross-tenant request must still be denied by the backend.

A verified internal document contains an attacker-added paragraph asking an agent to export unrelated user profiles. The document is readable by the requesting user. Which design best preserves the legitimate summarization task while containing the unauthorized action?

Reveal reasoning for every option

Best response: C

  1. A · Alternative

    Known provenance establishes origin, not authority for new actions. An authorized reader can still encounter attacker-controlled content.

  2. B · Alternative

    A coarse language filter can block legitimate instructions and miss subtle attacks. It leaves the export authority problem unresolved.

  3. C · Best response

    Data may inform the answer without granting authority. Independent permissions contain side effects while safe summarization can continue.

  4. D · Alternative

    A summary can launder an injected instruction into a cleaner-looking form; a second model does not create user authorization.

A model labels 200 eligibility answers “95% confident”; independent checking finds 166 correct. An evidence threshold instead answers 160 cases and gets 152 correct. What should the team report and use to decide automatic handling?

Reveal reasoning for every option

Best response: B

  1. A · Alternative

    The self-written confidence label is contradicted by the observed outcomes. It cannot serve as an established probability scale.

  2. B · Best response

    The three denominators describe different properties. Slice behavior and a safe fallback determine whether selective answering is usable.

  3. C · Alternative

    95% is accuracy among accepted cases, not all traffic, and the synthetic test does not establish production behavior.

  4. D · Alternative

    A single composite score hides the distinction between wrong answers and withheld answers and can conceal unequal access to service.

A safety policy requires review for the cases currently routed to it. Traffic is 40 cases/hour and 60% are routed. Two reviewers average six minutes/case, with no other duties assumed. What is the best launch response?

Reveal reasoning for every option

Best response: D

  1. A · Alternative

    The relevant calculation includes minutes per review: ideal capacity is 120 / 6 = 20 cases/hour, below the 24-case demand.

  2. B · Alternative

    Automatic release on timeout bypasses the stipulated review requirement precisely when oversight is under pressure.

  3. C · Alternative

    Changing the threshold changes which risky cases avoid review. It needs a justified policy decision, not a queue-only adjustment.

  4. D · Best response

    Demand exceeds even ideal capacity. Address it within the approved safety policy and measure realistic queue behavior; averages do not establish p95.

A worker approves an application to employer A with fields X and Y. Before execution, the proposal changes to employer B and adds field Z; the approval has not expired. Which behavior correctly handles the original approval?

Reveal reasoning for every option

Best response: B

  1. A · Alternative

    Workflow-level approval is not enough for materially different recipients or data. Expiry is only one part of approval validity.

  2. B · Best response

    Bind approval to the consequential proposal and state. Both content changes and current authorization matter at execution.

  3. C · Alternative

    Relevance and schema validity do not prove that the worker approved disclosure to a different employer.

  4. D · Alternative

    The recipient changed, so even the unchanged fields are being disclosed under a different consequence. A new decision is needed.

For a hypothetical GDPR deployment, the privacy owner determines that a user’s profile, summary and embedding are eligible for erasure, while a specified invoice must be retained under an applicable obligation. What should the implementation do?

Reveal reasoning for every option

Best response: A

  1. A · Best response

    Implement the authorized scope, including derived copies and recovery paths; a justified retained record does not justify continued personalization.

  2. B · Alternative

    Erasure is conditional. The scenario explicitly gives a justified retention obligation; engineers should implement that scoped determination.

  3. C · Alternative

    Hashing an identifier does not automatically make detailed linked records anonymous. The eligible derived copies remain in scope here.

  4. D · Alternative

    Encryption and account closure do not by themselves perform erasure or resolve the purpose and retention obligations.

A cloud provider maintains encrypted ePHI on behalf of a clinic business associate and has no decryption key. The parties agree that the customer implements patient-level authentication. Which conclusion is best supported?

Reveal reasoning for every option

Best response: C

  1. A · Alternative

    HHS explicitly states that maintaining encrypted ePHI on behalf of a covered entity or BA can create BA status even without a key.

  2. B · Alternative

    HHS permits particular agreed responsibilities to be satisfied through one party’s actions. Duplication is not the general requirement.

  3. C · Best response

    No-view changes the risk and control allocation, not all obligations. Each party must operate its assigned and otherwise applicable controls.

  4. D · Alternative

    The agreement is important, but encryption and authentication do not settle integrity, availability, administrative controls or actual operation.

An agency assistant uses a FedRAMP-certified cloud offering. A prototype adds an external model endpoint and tracing service. The team plans to process live federal information. What is the best next architectural action?

Reveal reasoning for every option

Best response: D

  1. A · Alternative

    Certification evidence has a defined offering and boundary; new external processing does not automatically inherit that assurance.

  2. B · Alternative

    FedRAMP is designed for evidence reuse. The agency must focus on its actual system and responsibilities rather than recreate all provider work.

  3. C · Alternative

    Minimisation can reduce risk but does not decide whether external services and processing paths are authorized for this system.

  4. D · Best response

    The agency authorizes its specific system use, configurations and integrations while reusing applicable provider evidence.

Two synthetic groups have different qualification base rates. A recommender achieves the same 80% true-positive rate and 10% false-positive rate for both, but the precision of recommendations differs. What follows?

Reveal reasoning for every option

Best response: A

  1. A · Best response

    Different base rates can yield different precision despite equal error rates. The justified policy requires context, not one universal metric.

  2. B · Alternative

    Precision depends on the relative counts of qualified and unqualified records, so the stated result does not by itself show a bug.

  3. C · Alternative

    These rates describe particular properties. They do not establish equal coverage, contestability, label quality or every fairness objective.

  4. D · Alternative

    Count parity is a possible policy consideration, not an automatic inference from the arithmetic or a substitute for a defensible decision.

A marketplace team wants to train a job-suitability model using past employer selections as qualification labels. Aggregate prediction accuracy is high, but workers report unexplained exclusion. Which next step most directly improves the fairness evidence?

Reveal reasoning for every option

Best response: C

  1. A · Alternative

    A more expressive model can reproduce historical selection patterns more accurately without making those patterns a valid qualification target.

  2. B · Alternative

    Proxies and biased historical processes can remain. Removing a field does not validate the target or demonstrate fair outcomes.

  3. C · Best response

    Investigate whether historical selection represents legitimate qualification and test delivered harms. Recourse helps identify and correct real errors.

  4. D · Alternative

    A generated rationale may not reflect the actual decision, and lack of complaints may reflect access barriers rather than lack of harm.

Terms you should be able to explain

Authority boundary
The point where trusted application policy decides whether an action may read data or produce a side effect.
Residual risk
The risk that remains after specified controls, with their tested limits and unresolved escape paths.
Indirect prompt injection
An attempt to redirect a model through content it was asked to process rather than through an authorized user instruction.
Provenance
Information about a record’s origin, version and transformations; it is separate from permission and factual correctness.
Least privilege
Granting only the functions, resources and duration needed for the intended task.
Approval binding
Connecting a reviewer’s decision to the precise consequential proposal, scope, expiry and resource state.
Automation bias
Over-reliance on an automated suggestion that weakens a person’s independent judgment.
Abstention
Withholding a decision or answer because conditions for safe handling are not met; its fallback and access effects still matter.
Calibration
Agreement between assigned probabilities and observed correctness frequencies under specified task and population conditions.
Coverage
The fraction of eligible incoming cases for which the system supplies the measured answer or decision.
Precision
The fraction of flagged or selected cases that are truly positive under the chosen reference labels.
Data controller
The actor determining purposes and means of a personal-data processing operation.
Data processor
An actor processing personal data on the controller’s instructions under the relevant arrangement.
Business associate
A HIPAA-defined relationship involving relevant functions/services and PHI on behalf of a covered entity or another BA; assess actual scope.
Inherited control
A control operated by another party whose relevant evidence and boundary are applicable to your system.
Contestability
A practical ability to understand, challenge and obtain correction of a consequential decision.
Selection bias
A distortion arising from which cases enter the observed dataset or receive labels, rather than only from model fitting.
Idempotency
A property or mechanism preventing a repeated request from producing an additional duplicate effect; it does not authorize the effect.
