LESSON 01 / OBJECTIVES 7.1, 7.2 / ~18 MIN

Build a team operating model before adding an agent

A developer agent is a program that can interpret a goal, inspect a codebase, invoke tools and revise its work. Productivity comes from making that loop reliable. A good answer in chat is only one intermediate result; the outcome is a change that works for users, survives review and can be operated by someone else. Domain 7 therefore connects developer convenience to the control and lifecycle decisions in Domains 5 and 6.

Use a concrete task contract: what behavior should change, where it lives, how success will be observed and which actions are authorized. For a proposed Quiet Hours feature, “improve scheduling” is weak. “When a user crosses a time zone, preserve the chosen local quiet interval; show the next activation time; test the daylight-saving boundary using synthetic dates” gives an agent an observable target. This is a design exercise, not a claim about the current Quiet Hours implementation.

Four layers answer four different questions

LayerQuestionExample evidence
Task and instructionsWhat should the agent do?Acceptance examples, repository map, CLAUDE.md
Tool policyWhich calls may it request or execute?Effective permission rules and approved MCP services
Execution environmentWhat can the process actually reach?Filesystem mounts, network policy, runner identity
Verification and ownershipWho establishes that the result works?Independent test, review, rollout owner and rollback

These layers are complementary. A README cannot stop a process reading a mounted secret; a container cannot decide whether an accessibility label is useful; a successful unit test cannot authorize publishing private data. Claude Code explicitly distinguishes model-facing project instructions from client-enforced settings. [D7-S02] The architecture should preserve that distinction even when a team uses a different coding assistant.

Worked case: a new developer joins NutriMind

Suppose a new engineer needs to add a dietary preference filter using synthetic meal records. Provide the actual module map, approved local runtime, fixture path, task contract and project-specific verification command. Give access to the necessary source tree and a staging API only if the task needs it. Keep production nutrition records and service credentials outside this exercise. The engineer should produce a focused diff, evidence for the filter behavior and a note about untested device behavior.

The onboarding acceptance criterion is practical: another engineer can reproduce the same outcome from the documented environment without borrowing the first developer's secrets or conversation history. “Claude opened successfully” is an installation check. It does not establish that the team can safely build, review or support a change. Keep a named owner for the shared configuration so broken defaults do not become each developer's private workaround.

LESSON 02 / OBJECTIVES 7.1, 7.3 / ~22 MIN

Configuration scope and precedence: resolve the effective policy

Configuration bugs often resemble model unreliability. One developer receives a permission prompt and another does not; a setting works in a terminal but not in a cloud runner. Before changing a prompt, identify which machine runs the agent, its version, its starting directory and the sources it loaded. A file committed in a repository reaches teammates only after they receive it, and machine-local files do not automatically travel into a cloud environment.

Know the ordinary settings stack

ScopeLocation or sourceIntended owner
ManagedOrganization-delivered policyOrganization administrator
Command lineSession settings supplied with --settingsSession launcher, within policy
Project local.claude/settings.local.jsonOne developer in this project
Shared project.claude/settings.jsonRepository team
User~/.claude/settings.jsonOne developer across projects

For ordinary overlapping keys, the table is highest first. Permission arrays merge across files instead of replacing one another; matching deny rules precede ask and allow. Environment-variable and flag interactions are key-specific. Read the current entry for the key rather than treating a single stack diagram as the complete evaluator. Run /status to see loaded setting sources and claude doctor to investigate rejected entries. [D7-S01] [D7-S03]

Worked case: “my local allow should win”

An organization denies a sensitive file read. A developer adds a local allow rule to debug a test. The relevant permission entries are evaluated together, and the deny still blocks the matching call. The solution is an approved synthetic fixture or a reviewed administrative policy change. Repeating the allow at a more specific scope does not make the sensitive read legitimate.

Conversely, when a normal preference is overridden by the shared project, a personal local preference can be appropriate. The important distinction is between resolving an ordinary value and evaluating permission rules. Also inspect whether a managed source limits lower-scope permission grants. Administrators must verify delivery on the surface actually used; a device policy file is not automatically present on a hosted runner. [D7-S21]

A small reviewed example

Download settings.example.json. It is strict JSON, researched against the documentation on 2026-10-13, and inert until you deliberately install it. It permits two narrowly described Git command patterns, asks for a push and denies selected built-in file reads. It is a teaching sample, not an exhaustive enterprise policy. Review Git configuration and indirect command execution before adopting command grants.

{
  "permissions": {
    "allow": ["Bash(git status)", "Bash(git diff *)"],
    "ask": ["Bash(git push *)"],
    "deny": ["Read(./.env)", "Read(./.env.*)"]
  }
}

Validate syntax, then test one permitted, one prompting and one denied operation with harmless fixtures. Capture expected and observed outcomes without displaying secrets. Do not merge the sample over an existing policy wholesale: preserve the team's current rules, check their combined behavior and confirm compatibility with the installed Claude Code release. A policy that parses but is not loaded provides no protection.

LESSON 03 / OBJECTIVES 7.1, 7.2 / ~24 MIN

Instructions, permissions and hooks solve different problems

Put durable project knowledge in instructions: where modules live, how to run the real checks, which generated files should not be hand-edited and what acceptance looks like. Keep it short enough to remain useful. A large pasted design archive makes important facts harder to find and becomes stale. Link detailed references from a concise repository map, and update the map when paths or commands change.

CLAUDE.md shapes the model's behavior; it is not a guaranteed enforcement layer. Use permission controls for tool decisions and an appropriate execution boundary for process access. A denied built-in file read does not prove that every allowed script is unable to open the same file indirectly. The official permission documentation describes these process limitations explicitly. [D7-S02] [D7-S03]

Hooks are event-driven programs

A hook runs because its event occurs, not because the model remembered a sentence. That makes hooks useful for mechanical checks or reporting. But the event determines what the hook can still prevent. A synchronous PreToolUse check runs before the call; PostToolUse runs after the effect. Exit code 2 blocks a PreToolUse call, while a PostToolUse result cannot undo an action that already happened. Background async command hooks cannot block the completed action through decision fields. [D7-S04]

Tricky point: “exit 2 always blocks” is too broad. The hook reference defines behavior per event; for example, PermissionRequest uses a structured decision rather than treating exit 2 as denial. A script crash, timeout and intentional blocking response are different outcomes. Test the exact event and failure behavior on the deployed version before relying on a hook for a required control. [D7-S04]

Worked case: generated code is formatted, but is it correct?

A team adds a post-edit formatter. The resulting code has consistent whitespace; it can still introduce a second charge after a timeout. Formatting provides useful fast feedback about one property. It does not validate business invariants. Likewise, a background test that finishes after a deployment has started cannot retroactively make deployment contingent on passing. A release gate must wait for the required result and fail according to an explicitly tested contract.

For a proposed Android screen change, separate mechanical feedback from behavioral verification. The formatter checks style; the compile step checks type and dependency consistency; a focused test checks state transitions; an observed device or emulator path checks whether the intended user can complete the interaction. Use the actual repository's commands after inspecting its scripts and build files. A familiar-looking Gradle task copied from another project may not exist or may verify the wrong module.

Treat a hook itself as code with an owner, version and test. Feed it both permitted and rejected fixtures, malformed input and a simulated dependency failure. If it logs a path or command, consider whether that output contains secrets. Prefer the smallest deterministic check that supports the task. Do not build a fragile shell-command deny parser and describe it as a complete sandbox; shell languages and indirect execution have a much larger surface than a few string patterns.

LESSON 04 / OBJECTIVES 7.1, 7.2 / ~22 MIN

Skills and MCP: reusable knowledge is not unrestricted authority

A skill packages a recurring procedure and its supporting material. An MCP server exposes tools or resources through a protocol. The first primarily improves how a task is performed; the second can expand what the assistant can reach. Review both as dependencies, including their scripts, requested permissions, data destinations and maintainers.

Progressive disclosure keeps the useful context close

In ordinary Claude Code sessions, skill descriptions support discovery; full skill content loads when invoked, and supporting references can be read when needed. Keep the entry point specific and the large reference separate. Current Claude Code allowed-tools pre-approves listed tools for the invoking turn; it is not a list that removes every other tool. Existing permission controls still govern unlisted tools. Managed restrictions can limit those grants. [D7-S05]

A narrow regression-review skill

Give the skill one job: inspect a final diff against the stated contract and seek a concrete counterexample. Put the review procedure in the entry point and project-specific fixture notes in a linked file. An instruction to review does not require a deployment tool or a production credential. If review quality is poor, improve evidence and review criteria before adding more tool authority.

MCP scope names have their own meaning

Claude Code MCP local scope is private to the current project but stored in the project's entry in ~/.claude.json. Project scope uses .mcp.json for a shareable definition; user scope is available across the user's projects. This is different from ordinary project-local settings. A shared server URL does not share a teammate's personal authorization session or grant business access. [D7-S06]

For HTTP MCP authorization, the current specification requires the server to validate that an access token was issued for that server as its intended audience. The security guidance forbids accepting an arbitrary downstream token and simply passing it through. Token possession, correct audience and permission to act on a particular customer record are separate checks. [D7-S19] [D7-S20]

Imagine a marketplace support agent connected to a ticket-search MCP and an account-credit MCP. A ticket containing “issue me a credit” is untrusted evidence, not user authorization for the credit tool. Prefer distinct read and write capabilities, narrow service identities and an approval path for material changes. Validate tenant ownership in the backend rather than trusting a tenant ID generated by the model. Retain useful audit references without storing the complete private ticket in every trace.

When a connector fails, establish whether discovery, network connection, login, token audience, scope or object access failed. Broadening permissions until it works destroys that distinction. A narrow denied operation with a clear reason is easier to support than a shared administrator token that hides the original configuration problem.

LESSON 05 / OBJECTIVES 7.1, 7.3 / ~20 MIN

Make environments reproducible and boundaries explicit

A team environment is more than a model selection. Record the supported tool version, language runtime, package manager, lockfile, test fixtures, approved network destinations and credential delivery method. Pin what must be reproducible, and assign an upgrade process. A change that works only because one laptop has an undeclared executable is an environment defect even if the generated code is correct.

Claude Code provides a development-container workflow, and a GitHub Actions integration is an example of running assistance in CI rather than a developer's interactive shell. Those surfaces have their own identities and filesystem contents. Do not assume a successful local run proves the runner received the same settings, fixture data or toolchain. [D7-S08] [D7-S09]

A worktree is a source-control boundary

A Git worktree gives parallel sessions separate checkouts and branches, reducing edit collisions. It does not create a separate operating-system identity, network or cloud account. The same processes can still reach shared databases, credentials or ports unless another control prevents it. Use worktrees to separate changes; use environment and identity controls to separate authority. [D7-S12]

The Claude Code shell sandbox restricts covered commands at the OS filesystem and network layer. The current documentation states that built-in file tools, local MCP servers and hooks operate outside that shell boundary. Configure the relevant tool policies and protect those additional processes separately. “Sandbox enabled” is a statement about a defined boundary, not proof that every integration is confined. Platform support also differs; verify the operating system actually used. [D7-S07]

Worked case: an AI reviewer on a pull request

Suppose a team wants CI to explain risky changes. The pull request's text and files are untrusted input. Run review with the minimum repository privileges and a synthetic or read-only environment. Avoid giving the reviewer a deployment credential merely because its job runs in the deployment repository. Ensure the workflow does not execute untrusted branch code with privileged secrets. GitHub's security guidance specifically treats untrusted workflow input and secret access as separate concerns. [D7-S10]

A container narrows some boundaries only when its mounts, process privileges and network are configured accordingly. Mounting the developer's home folder or host control socket can undermine the intended isolation. A test credential should be scoped, short-lived where supported, and revoked through an owner-managed process. Do not place production secrets in committed settings, an instruction file, a fixture or a pasted troubleshooting transcript.

For team rollout, create a short smoke path: open the approved project, verify loaded configuration, inspect a harmless file, run the intended local check and observe a denied or prompting operation using dummy data. Repeat on the supported IDE and runner surfaces. Record gaps honestly. A reproducible failure is useful evidence; silently disabling a control to make onboarding green creates a support problem that will return during an incident.

LESSON 06 / OBJECTIVES 7.2 / ~22 MIN

Use AI to accelerate a verifiable engineering loop

The most useful workflow is small enough that its assumptions can be checked. Start with the user-visible behavior, inspect the relevant code and callers, identify a failure example, make a focused change, run an appropriate check and review the resulting diff. The assistant can help at every step. The responsibility to define acceptance and authorize side effects remains with the team.

Anthropic's current best-practice guidance emphasizes giving Claude a runnable verification signal and showing evidence such as command output or observed application behavior. It also describes independent review as a way to challenge the implementing agent's conclusions. These are useful workflow practices, not guarantees that any particular model will find all defects. [D7-S11]

A prompt that gives the model something to prove

Outcome: one logical checkout must create at most one charge,
even when the provider commits and its reply is lost.
Read the retry caller and provider adapter first.
Use the offline fixture; do not contact a payment service.
Show a failing business invariant, make a focused fix,
then run the check and report the actual exit status.
Preserve tenant separation and reject a changed amount
for the same operation. Do not weaken the assertions.

This prompt supplies failure semantics and an observable invariant. “Make retries robust” leaves the assistant to guess which errors are retryable and what must remain stable. The stronger prompt also makes independent review possible: another person can look for a counterexample without needing the original conversation.

Choose verification by consequence

For a typo, inspect the result. For a parser or state transition, use a compact fixture that distinguishes correct from incorrect behavior. For money or authorization, include a meaningful rejected case and assert that rejection caused no side effect. For an Android interaction, inspect the actual screen path and assert the intended user outcome using stable identifiers where available. For a production change, use the team's real deployment and rollback checks. More tests are useful only when they resolve a real uncertainty.

A test that calculates its expected value by calling the same helper it is checking can repeat the defect. Instead, write the invariant in business terms. The lab's expected “one order charges 1,200 cents once” is independent of how a key is generated. A fresh reviewer should inspect surrounding code, not just the changed lines: a perfect helper can be called with a fresh operation ID on every retry and still produce duplicates.

Use independence deliberately. Give a reviewer the task contract, diff, relevant context and evidence, and ask it to challenge authorization, partial failure, duplicate delivery and stale state. Avoid feeding it only the implementer's persuasive explanation. A second model is still fallible and may share assumptions, so a concrete counterexample or an independently executed check is stronger than two agreeing summaries.

Download the review and measurement worksheet. At handoff, state what changed, why, which commands actually ran, what was observed and what remains unverified. Keep the result reproducible after the chat is gone. That is developer enablement: reducing the next engineer's uncertainty, not merely generating today's code faster.

LESSON 07 / OBJECTIVES 7.2 / ~22 MIN

Measure net productivity without confusing activity with value

Generated lines, accepted suggestions and prompt counts describe activity. They do not establish that a team delivered a useful change faster or with less risk. The assistant might shorten initial implementation while increasing review, rework or incident load. Measure the whole workflow and preserve quality constraints; otherwise a productivity target can reward moving work onto someone else's queue.

What current industry research actually says

METR's July 2025 randomized experiment involved 16 experienced open-source developers completing 246 tasks in repositories they knew well. With early-2025 AI assistance allowed, completion took 19% longer on average. The authors describe it as a snapshot in a specific setting, not a universal verdict on coding agents. [D7-S13]

METR's February 2026 update reports later results consistent with possible speedup, but emphasizes selection effects and measurement difficulties. Developers and tasks were increasingly selected out of AI-disallowed work; parallel-agent use also complicated time measurement. The authors regard the data as weak evidence for the size of the change. Do not present the 2025 slowdown as today's guaranteed outcome or the later estimates as a universal reversal. [D7-S14]

DORA's 2025 report characterizes AI as an amplifier of existing organizational strengths and weaknesses. That supports investigating the surrounding system: task clarity, feedback speed, review capacity and dependable environments. It does not supply a causal percentage that can be pasted into every business case. [D7-S15]

Worked arithmetic: a faster first draft can yield a small net gain

Comparable task, illustrative meanBaselineAI-assisted
Initial implementation70 min45 min
Review15 min25 min
Rework5 min15 min
Total engineer effort90 min85 min

Net effort reduction = (90 − 85) ÷ 90 = 5.56%

These are invented teaching values. The initial implementation reduction is 35.71%, but the net reduction is only 5.56%, before training, tool and support costs. Neither value is cash saved unless the organization changes spending or uses the capacity productively. Also separate active engineer effort from elapsed delivery time: waiting three hours for review can dominate a small coding improvement.

Design a small pilot around comparable tasks, recorded complexity and a fixed completion definition. Include review time, a follow-up window for escaped defects, severity, tool cost and developer experience. Where feasible, assign assistance before work starts rather than letting people put only easy tasks in the assisted bucket. Record missing and abandoned tasks. Compare uncertainty and variation, not just two attractive averages.

A useful decision might be “continue AI-assisted fixture creation for this service; revise authorization-change workflow because review burden rose.” It need not be “AI everywhere” or “AI nowhere.” Keep a stopping rule for unacceptable defects and a human owner for interpreting the data. The exam skill is selecting a defensible workflow under constraints; the practical skill is finding out whether it improves your own team's outcomes.

LESSON 08 / OBJECTIVES 7.3 / ~24 MIN

Debug the failing layer with discriminating evidence

“The AI failed” is a symptom label. A useful diagnosis identifies which layer produced the wrong result and what observation would distinguish competing causes. Start with one failed user operation, its timestamp, deployment version and correlation identifiers. Preserve the input's relevant structure while removing sensitive content. Change one explanatory variable at a time whenever possible.

SymptomCompeting explanationUseful discriminating observation
One laptop cannot searchRuntime, path, installation or configurationApproved binary version, working directory, loaded sources
All requests are rejectedAuthentication, scope, rate limit or provider faultError category, request IDs, account context, official status
Answer cites an old policyRetrieval version, filtering or generation errorRetrieved source IDs, dates, access verdict and supplied evidence
Tool says success, action missingTransport success versus business failureResponse schema, application status and external system state
Duplicate external actionRetry, callback redelivery or reconciliation defectStable operation ID, attempt IDs and provider records

Claude Code documents claude doctor for installation/configuration checks and /mcp for server status. Claude API errors carry categories and request identifiers useful for provider-side investigation. Preserve identifiers and timing through an approved private support path; do not substitute the model's explanation for the actual response. [D7-S18] [D7-S16]

HTTP 200 is one observation, not the whole outcome

A fictional booking endpoint returns HTTP 200 with {"status":"rejected","reason":"slot_taken"}. The transport exchanged a valid response. The requested booking did not happen. Another endpoint returns status: pending; completion requires later polling or a callback. An agent that announces success immediately has collapsed accepted, pending and completed states. Define and validate the application schema, terminal state and expected external effect.

Streaming adds another boundary: an initial successful HTTP response can be followed by an error event. Client behavior must consider the complete stream contract rather than treating the first status line as final success. The API's current error documentation calls out errors during streaming. [D7-S16]

Worked case: the lost reply that creates a duplicate

The right fix is not merely “retry fewer times.” Preserve the identity of the business intent across attempts, scope it to the tenant and operation, reject conflicting payload reuse and reconcile uncertain outcomes. Transport attempt IDs should vary for tracing; the business operation ID should remain stable. If a provider offers an idempotency contract, inspect its retention window and conflict behavior. Once that window expires, a blind retry may no longer deduplicate.

In production, persist intent and reconciliation state durably, make concurrent admission atomic, and verify the provider's actual contract. The offline lab deliberately omits these production mechanisms to isolate the root cause. Its assertion checks the business effect, so changing log messages or catching every exception cannot make the defect disappear. This is the debugging habit to transfer to your projects: prove what happened outside the agent's narrative.

LESSON 09 / OBJECTIVES 7.3, 7.1 / ~20 MIN

Operate incidents with bounded authority and a safe evidence trail

During an incident, urgency makes broad tool authority tempting. Keep investigation and intervention explicit. Read-only observation can establish impact and likely cause; a write action can change evidence, duplicate an external effect or expand the blast radius. Agree in advance which reversible containment actions the on-call role may perform and which require incident-command approval. The appropriate boundary depends on the system and existing operating policy.

A proposed nutrition assistant returns stale meal recommendations after an index rollout. First inspect the deployment, source versions, index routing and request traces using synthetic or authorized sanitized examples. A model upgrade is premature if retrieval supplied last month's records. Likewise, a local credential failure should not be labeled a provider outage, and a broad provider outage should not be “fixed” by repeatedly rotating application secrets.

Contain, diagnose, recover, reconcile

Containment might temporarily return a deterministic search result, disable a risky write tool or route a high-impact request to an existing human queue. State the user impact: reduced capability, slower responses or unavailable actions. Do not silently announce normal operation while using a degraded path. Diagnosis then tests the strongest competing hypotheses with discriminating evidence. Recovery requires an observed safe user outcome, followed by reconciliation of pending or partially completed operations.

Retries are also load. During a rate-limited or overloaded dependency incident, unbounded retries can amplify the failure. Use a bounded retry budget for eligible errors, appropriate delay and jitter, and an overall deadline. Do not retry authorization failures by changing identities, and do not repeat uncertain writes without the operation's idempotency/reconciliation contract. Error category and business semantics determine the response; “all errors are transient” is an unsafe simplification.

Correlate events without collecting everything

Claude Code's current monitoring documentation supports OpenTelemetry and a prompt.id correlation attribute for related events. Content logging is separately controlled and can expose prompts, tool results or model output when enabled. Keep the smallest evidence needed for diagnosis, apply access and retention controls, and verify exporter fields on the deployed version. Token totals or tool counts alone do not establish a successful user operation. [D7-S17]

Support bundles need inspection: runtime dumps may contain secrets even when their filename sounds technical. Claude Code specifically warns that a heap snapshot can contain conversation strings and credentials. Prefer a minimal synthetic reproducer, relevant versions, timestamps, error categories and request IDs; manually inspect what you share. [D7-S18]

Download the incident worksheet. Fill in the incident owner, affected journey, scope of impact, approved observations, write approvals, rollback criteria and backlog reconciliation. Keep raw private payloads out of a public issue. The worksheet intentionally asks for both transport and business outcomes so a healthy HTTP dashboard cannot conceal an application failure.

After recovery, choose a small prevention change tied to the cause: a version-routing assertion, a stable-key regression, a clearer error category or a missing runbook step. Record an owner and verification date. “Improve the prompt” is not an adequate corrective action when the failure came from a stale index, credential scope or duplicate external write. Operational enablement means the next responder can reach the same diagnosis with less uncertainty.

LESSON 10 / OBJECTIVES 7.1, 7.2, 7.3 / ~45 MIN

Practical lab: reproduce, fix and review a retry defect

The exercise applies observable verification and independent review from the documented development workflow; its provider simulation and assertions are original teaching fixtures. D7-S11

This lab is fully offline and uses only Python 3.9+ standard-library modules. It makes no network calls, writes no files and moves no real money. Download the five files together into a new exercise folder. The buggy mode intentionally fails; fixed mode contains the reference behavior. The business setting is a marketplace checkout, but the same uncertainty occurs in ticket creation, notification delivery and other external side effects.

lab.py · CLAUDE.md · settings.example.json · review-and-measure.md · incident-runbook.md

Step 1 — State the invariant before reading the implementation

Write: one tenant's logical order must create at most one charge for its agreed amount, including a lost reply and duplicate client delivery. A different tenant's order must remain independent. Reusing the same intent with a changed amount must be rejected without a new charge. This contract is stronger than “the function eventually returns success.” Expected outcome: you can explain what the test must prove without mentioning the key-generation algorithm.

Step 2 — Reproduce the red result

python3 lab.py buggy

Expected outcome: a nonzero exit and an assertion saying one business intent created three charges instead of one. The first attempt commits and loses its reply; a retry uses a new key; a repeated client delivery uses another new key. Inspect the provider's state and the caller together. The failure is intentional teaching evidence, not a broken installation. Do not remove the assertion to obtain a green result.

Step 3 — Trace identity across attempts

Read Checkout.pay and Provider.charge. Identify the business identity tuple, the attempt counter and the point where the simulated timeout occurs. Sketch a sequence with “committed externally” before “reply lost.” Explain why the caller cannot conclude that nothing happened. Predict which identifier should remain stable and which should change before running the reference.

Step 4 — Verify the reference fix and rejected cases

python3 lab.py fixed

Expected outcome: exit zero with PASS: one intent/one charge, tenant scope, payload conflict, money validation. The check observes the number and total amount of provider-side charges, tests a second tenant, rejects conflicting amount reuse, and rejects zero, negative, fractional and boolean money input. These are business and trust-boundary properties; they do not assert a particular hash string.

Step 5 — Challenge the fix as a reviewer

Use the review worksheet without the implementer's narrative. Ask what happens after a process restart, simultaneous calls, a provider deduplication expiry or a permanently unknown result. Expected outcome: record that this in-memory single-process toy does not solve those production cases. Propose durable intent storage, atomic admission and provider reconciliation as additional requirements. Do not claim the toy is a payment library or that local tests establish a provider's guarantee.

Step 6 — Transfer one idea into a project proposal

Choose a synthetic task in Quiet Hours, NutriMind or a marketplace project. Identify the actual caller, state transition, external side effect and verification command only after inspecting that repository. Draft a small task contract, an evidence-based workflow and a rollback or recovery note. If using Claude Code, review the supplied instructions and inert settings example against your installed release; keep production credentials out of the exercise. Expected outcome: a reproducible proposal another engineer can review without your chat history.

Acceptance: you can reproduce the expected red and green runs, explain the unknown-outcome retry, distinguish instruction from enforcement, identify the lab's persistence and concurrency limits, and hand off a project-specific verification plan. Finish by answering the checks below and explaining why the attractive alternatives fail. This is preparation for architectural judgment, not a prediction of your live exam score.

    The documented field affects permission prompting; it is more than descriptive text, although other controls still apply.

A teammate receives a committed .mcp.json definition for a ticket service but cannot access tickets. Another developer proposes committing their OAuth token alongside the definition. What is the best next step?

Reveal reasoning for every option

Best response: D

  1. A · Alternative

    A configuration scope controls where a definition is available; it does not legitimately transfer another principal's identity.

  2. B · Alternative

    Token passthrough bypasses the intended audience boundary and is explicitly forbidden by MCP security guidance.

  3. C · Alternative

    Refresh tokens are sensitive credentials; committing one creates continuing access risk rather than solving authorization correctly.

  4. D · Best response

    Correct. A shared endpoint definition and personal authorization are separate. Backend object authorization must still hold.

Two coding sessions use separate worktrees. Both can reach the same production database through an inherited environment credential. What does the worktree separation establish?

Reveal reasoning for every option

Best response: B

  1. A · Alternative

    A source-control checkout does not partition the database or the authenticated account.

  2. B · Best response

    Correct. Worktrees separate source files and branches, not every host resource or service privilege.

  3. C · Alternative

    Environment credentials and other host resources can be shared without any secret being committed.

  4. D · Alternative

    Git coordination does not serialize arbitrary authenticated database operations. Both sessions can still use their inherited database credential simultaneously.

A comparable-task pilot reports baseline effort of 70 minutes implementation, 15 review and 5 rework. Assisted effort is 45, 25 and 15 minutes respectively. Before adoption overhead, which conclusion is justified?

Reveal reasoning for every option

Best response: B

  1. A · Alternative

    The initial implementation reduction ignores work transferred into review and rework.

  2. B · Best response

    Correct. Totals are 90 and 85 minutes: (90−85)/90 = 5.56%. That is a task-level effort estimate, not a universal business effect.

  3. C · Alternative

    Time capacity and cash expenditure are different; unchanged payroll does not automatically fall when a task is faster.

  4. D · Alternative

    The proposed exclusion removes a material consequence of the workflow and yields a misleading comparison.

A manager cites METR's 2025 slowdown as proof that coding agents cannot improve this year's team productivity. Which response best represents the primary evidence?

Reveal reasoning for every option

Best response: C

  1. A · Alternative

    The update explicitly cautions that selection effects limit inference about the magnitude of later speedup.

  2. B · Alternative

    Experience alone does not make tool versions, tasks, environments and workflows interchangeable.

  3. C · Best response

    Correct. Preserve both studies' limits and evaluate the actual task population and full workflow rather than promising a universal effect.

  4. D · Alternative

    Real-world experiments provide complementary evidence; benchmarks and workplace outcomes answer related but different questions.

A checkout provider creates a charge but its reply is lost. The client retries with a newly generated idempotency key and obtains another success. What should the regression establish?

Reveal reasoning for every option

Best response: A

  1. A · Best response

    Correct. This tests the external business invariant, tenant separation and conflict behavior independently of the implementation algorithm.

  2. B · Alternative

    Bounded retries and unique attempt IDs are useful, but neither prevents duplicate business effects.

  3. C · Alternative

  4. D · Alternative

A booking tool returns HTTP 200 with status=pending. The assistant tells the customer the reservation is confirmed. What is the most direct correction?

Reveal reasoning for every option

Best response: D

  1. A · Alternative

    The integration must represent pending versus completed states; a model change leaves the incorrect contract intact.

  2. B · Alternative

    Accepted or pending work may fail later; transport success is not a guarantee of eventual business completion.

  3. C · Alternative

    A fresh write can create duplicates and does not resolve the original operation's uncertainty.

An incident investigator has a minimal synthetic reproducer, request IDs and a heap snapshot from a failed agent session. What is the best support handoff?

Best response: C

  1. A · Alternative

    Heap snapshots can contain conversations and credentials; public attachment can disclose sensitive data.

  2. B · Alternative

    Renaming does not remove the sensitive strings contained inside a process snapshot.

  3. C · Best response

    Correct. Preserve useful correlation evidence while minimizing and inspecting the data shared through the authorized support path.

Terms you should be able to explain

Effective configuration
The combined, actually loaded settings and policies that determine behavior for a particular session and surface.
Instruction versus enforcement
Instructions influence model behavior; enforcement is implemented by a client, backend or execution boundary.
Permission scope
The context in which a configuration or tool grant applies; ordinary settings and MCP use distinct scope models.
Progressive disclosure
Loading a compact discovery description first and detailed procedures or references only when needed.
Token audience
The resource server for which an access token was issued; accepting the wrong audience breaks an authorization boundary.
Worktree
A separate Git checkout used to separate source changes; it is not an operating-system sandbox.
Business operation ID
A stable identity for one intended business action, preserved across transport attempts and duplicate deliveries.
Idempotency
Repeated execution of the same logical request does not create additional unintended effects under a defined contract.
Unknown outcome
The caller lacks confirmation of whether an external effect committed, as when a reply is lost after processing.
Discriminating observation
Evidence chosen because it helps distinguish competing explanations for a failure.
Net productivity
Useful accepted outcomes relative to total effort and cost, including review, rework and operational consequences.
Reconciliation
Comparing intended and actual external state and resolving pending, missing or duplicate effects safely.
