Q1 · Instrument the actual bottleneck

Select 1.

A fictional animation studio wants Claude to shorten delivery of subtitle packages. Editors spend little time translating but wait days for licensors to approve terminology. The proposed business case assumes translation is the delay. No one has measured time in each state, and the licensor approval process cannot change this quarter. Which next step best establishes whether an AI intervention can meet the delivery goal?

  1. Incorrect. Benchmark translation accuracy on finished episodes and approve development if the model exceeds the existing editorial quality threshold.

    Translation quality matters later, but a quality benchmark cannot establish that faster translation addresses the dominant delivery delay.

  2. Incorrect. Prototype automatic terminology approval and demonstrate its possible impact before revisiting the licensor agreement with the business sponsor.

    This changes an explicitly fixed authority boundary, so the prototype cannot validate the proposed intervention under current constraints.

  3. Correct. Measure elapsed time by workflow state and compare the addressable translation interval with the required delivery improvement.

    State-level evidence distinguishes work the proposed system can accelerate from waiting time outside its authority and scope.

  4. Incorrect. Calculate subtitle tokens per episode and use the estimated inference cost to prioritize the smallest affordable translation model.

    Inference economics optimize a candidate solution without establishing that its addressable interval can materially improve the stated outcome.

Frame the problem around delivery states before choosing a model. If approval waiting dominates and cannot change, even perfect translation acceleration may miss the target. Establish the baseline, addressable time and authority constraints, then decide whether to proceed or redefine scope.

Q2 · Separate prediction from explanation

Select 2.

A fictional district-heating operator already has a validated tabular forecast of hourly heat demand. Dispatchers struggle to understand forecast changes and ask for a Claude replacement. The engineering owner stipulates that the numeric forecast must remain under the existing validation regime; the real unmet need is explaining changes using weather notes and maintenance reports. Select TWO recommendations that meet that need without expanding the prediction scope.

  1. Incorrect. Train dispatchers to treat explanations as provisional forecasts and select the value they believe best reflects current weather conditions.

    This conflates a communication aid with an alternative prediction channel and transfers an unresolved validation problem to dispatchers.

  2. Incorrect. Let Claude correct forecast values whenever maintenance notes appear newer than the last structured input used by the predictor.

    Recency alone supplies neither validated correction logic nor delegated authority to change the numeric output in this design.

  3. Correct. Evaluate explanation faithfulness and dispatcher comprehension separately from the forecast model’s existing numeric prediction acceptance tests.

    The new capability has its own failure modes; preserving forecast tests alone does not establish useful, supported explanations.

  4. Correct. Keep the validated forecast as the numeric authority and let Claude explain its supplied drivers using linked operational evidence.

    This places language generation around the existing predictor while preserving the owner’s explicitly assigned authority over numeric forecasts.

  5. Incorrect. Replace the predictor with Claude and preserve the validation regime by comparing average forecast totals over one historical month.

    Monthly average agreement can conceal hourly errors and does not satisfy the owner’s requirement to preserve the validated predictor.

The architecture should separate numeric prediction from evidence-based explanation. Preserve the validated service as the authoritative forecast and evaluate the language layer against its actual job: explaining supplied drivers clearly without inventing causes or changing values. This directly addresses the unmet user need.

Q3 · Bind approval to application state

Select 1.

A fictional museum uses Claude to draft collection-transfer instructions. A curator approves a draft, but a background process can update the destination afterward. The execution worker currently checks only that an approval exists for the transfer ID. The museum requires the curator to approve the exact destination that receives the collection. What architectural change best enforces this requirement when approvals and execution are asynchronous?

  1. Incorrect. Retain approval at transfer-ID level but notify the curator whenever the background process updates the destination before execution.

    Notification supplies awareness but does not stop execution under an approval that no longer covers the current destination.

  2. Incorrect. Send a fresh summary of the transfer to Claude immediately before execution and ask whether the original approval still appears applicable.

    A semantic similarity judgment cannot enforce that the actual destination and version equal those approved by the curator.

  3. Correct. Bind approval to the transfer version and destination, and reject execution when either differs from the approved state.

    Version-bound authorization prevents an approval for one destination being reused after the application state changes before execution.

  4. Incorrect. Lock destination editing in the curator interface while allowing the background process to update the worker’s destination field normally.

    An interface restriction leaves the identified background mutation path available and therefore fails the stated exact-state requirement.

Approval is an input to execution, not a permanent property of a transfer ID. Check a version or digest that includes the destination at commit time. If relevant state changes, return the case for renewed approval before any instruction is executed.

Q4 · Carry authorized memory forward

Select 2.

A fictional conservation charity runs a seasonal grant-writing assistant. Users may revoke access to a project between sessions, while approved narrative facts should persist for projects they still own. Engineers propose retaining a summary under each user ID and loading it automatically at every login. Select TWO additions that make persistent context useful while respecting changing project authority and correcting stale facts.

  1. Incorrect. Treat the remembered summary as user-owned content that remains accessible after project access is revoked because it was previously generated.

    Generation does not erase the underlying project restriction; previously authorized access does not establish indefinite permission to reuse facts.

  2. Incorrect. Keep the summary under the project’s display name and ask Claude to infer which project the user currently means.

    Display names can collide or change, and model inference does not replace explicit identity and permission binding during assembly.

  3. Correct. Provide an owner-controlled correction path and rebuild affected summaries when the approved source narrative changes or is withdrawn.

    Durable memory can become stale, and a correction mechanism prevents obsolete narrative facts persisting beyond the approved source.

  4. Correct. Store project identity, provenance and revision metadata with remembered facts, then recheck current project access before loading them.

    Memory selection must reflect current authorization; linking facts to their source project enables access checks and later correction.

  5. Incorrect. Preserve all prior summaries and choose the longest available version because it is most likely to retain the original approved details.

    Length does not establish authority, freshness or correctness; retaining obsolete summaries without revision selection compounds the stale-state problem.

Memory belongs in a governed context-assembly path. Persist compact facts with stable project identity and provenance, verify access at retrieval time, and let owners correct or withdraw them. The useful continuity comes from authorized current state, not automatic loading of historical user summaries.

Q5 · Bound iterative refinement

Select 1.

A fictional accessibility publisher generates audio-description scripts. A critic reliably detects missing spatial cues, and one revision improves blind reviewers’ comprehension. Further revisions sometimes oscillate between concision and detail. Release requires a stable maximum processing time, and reviewers accept manual handling of unresolved cases. Which pattern best retains the measured benefit while meeting the operational constraint for each submitted script?

  1. Incorrect. Use a critic that restarts generation whenever either criterion fails and allow completion time to vary with script complexity.

    Unbounded restarts preserve the oscillation and conflict with the stated requirement for a stable maximum processing time.

  2. Incorrect. Run a fixed number of independent script generators and select the shortest candidate without using the critic’s spatial-cue assessment.

    Shortest length is not the validated accessibility criterion, so voting among drafts discards the evidence motivating the change.

  3. Incorrect. Route scripts by word count to either a concise or detailed prompt and retire the critic once both prompts are deployed.

    Word count does not establish spatial-cue completeness, and removing the measured critique step has no supporting evaluation evidence.

  4. Correct. Use a bounded generator–critic revision loop with explicit acceptance criteria and route unresolved scripts to the editorial queue.

    A bounded loop captures the demonstrated revision benefit while giving the system a definite stopping point and unresolved-case path.

An evaluator–optimizer pattern fits because critique measurably improves the output. The time constraint changes its termination design: cap iterations, evaluate explicit criteria, and expose unresolved cases for manual handling. A useful critic does not justify an unbounded attempt to satisfy competing objectives.

Q6 · Parallel checks need a join rule

Select 1.

A fictional food-labeling platform must check allergen wording, translation consistency and packaging dimensions before releasing artwork. All three checks use the same frozen artwork revision and can run independently. The prototype releases as soon as any two checks pass, because this reduced latency in a demonstration. The quality owner says each check is mandatory. Which design best meets that requirement without imposing unnecessary sequential work?

  1. Incorrect. Have an orchestrator decide which checks the artwork needs and request the remaining checks only when its initial judgment is uncertain.

    The checks are already specified as mandatory, so making their execution discretionary conflicts with the agreed quality policy.

  2. Incorrect. Keep the two-of-three rule but assign the most capable model to whichever check historically fails most often in production.

    Improving one checker does not satisfy the owner’s requirement that all three mandatory checks pass before release occurs.

  3. Correct. Run checks concurrently on the frozen revision and release only after all required results pass for that same revision.

    Parallel execution is compatible with mandatory checks when the join condition requires every result and binds them to one revision.

  4. Incorrect. Run the three checks sequentially and release after the second pass, retaining the third result for later audit review.

    Sequential order adds latency while the early release condition still omits a mandatory check from the actual release decision.

Use parallel sectioning for independent checks, coupled with a deterministic all-required join. Bind every result to the frozen artwork revision so late results cannot authorize changed artwork. The architectural issue is the completion condition, rather than whether concurrency itself is appropriate.

Q7 · Make specialist results mergeable

Select 2.

A fictional marine insurer delegates storm-event research to three specialists covering weather observations, vessel tracks and port closures. Reports use incompatible event times and disagree on whether an observation is confirmed. The lead cannot reliably combine them, although the subtasks are independent and parallel research meets the deadline. Select TWO changes that preserve parallelism and improve the reliability of the final event reconstruction.

  1. Incorrect. Select the report containing the most observations as authoritative and ask the lead to harmonize every other report to its timeline.

    Observation count does not establish source reliability, and forced harmonization can conceal unresolved evidence rather than verify the reconstruction.

  2. Incorrect. Replace the parallel specialists with sequential calls using identical prompts so later workers can repeat the earlier workers’ conclusions.

    Serial repetition sacrifices independence and latency without supplying the missing event schema or resolving the source evidence conflicts.

  3. Correct. Require a shared event schema with UTC timestamps, source references and explicit observed-versus-inferred status for every material finding.

    A common representation makes findings comparable while preserving uncertainty and evidence needed to judge conflicts during final synthesis.

  4. Correct. Have the lead verify conflicting material claims against the cited evidence and record unresolved disagreements rather than silently averaging them.

    Verification and explicit conflict handling prevent plausible but incompatible specialist assertions becoming an unsupported single account of events.

  5. Incorrect. Give every specialist the lead’s entire conversation and retain free-form prose so each report can preserve its local narrative style.

    Extra context does not solve incompatible evidence contracts, and free-form reports preserve the specific merge failure described here.

Keep independent research parallel, but standardize the handoff contract. The lead needs comparable times, provenance and uncertainty to reconcile findings. Material conflicts require evidence checks or an explicit unresolved result; producing a smooth narrative is not sufficient when the sources disagree.

Q8 · Account for coordination overhead

Select 3.

A fictional railway planning team considers specialists for three independent corridor studies. Each worker needs a different local evidence bundle. The final recommendation must reconcile shared rolling-stock assumptions, and the team has a strict total token budget. Select THREE design measures that make the multi-agent proposal reviewable before approving it, given that parallel execution alone has not demonstrated either quality or economic benefit.

  1. Incorrect. Estimate cost using the longest worker’s output only because independent parallel execution prevents other workers contributing to overall usage.

    Parallelism reduces some elapsed time but does not make other workers’ tokens disappear from the system’s aggregate resource consumption.

  2. Incorrect. Evaluate each corridor report separately and infer final recommendation quality by averaging the three individual report scores after completion.

    Component scores cannot establish that the synthesis reconciles shared resources; a good local report may imply an infeasible combined plan.

  3. Correct. Include worker context, duplicated evidence and lead synthesis tokens in the per-completed-study cost model and budget enforcement.

    Total system consumption includes coordination and repeated context; counting only the final answer would understate the architecture’s real cost.

  4. Correct. Define a shared assumption ledger and require the lead to reconcile rolling-stock conflicts before finalizing the cross-corridor recommendation.

    Independent studies still share consequential assumptions, so an explicit reconciliation step is needed before their recommendations can be combined.

  5. Correct. Benchmark the specialist design against a single-agent baseline using the same corridor coverage and final recommendation rubric.

    Comparable coverage and outcome criteria reveal whether the extra orchestration improves the actual planning task enough to justify its cost.

Parallel corridors are a plausible decomposition, but the decision depends on measured end-to-end value. Compare against a fair baseline, account for every participant’s consumption, and reconcile shared assumptions explicitly. Independence in evidence collection does not imply that the final planning decisions are independent.

Q9 · Preserve cross-document dependencies

Select 1.

A fictional aerospace supplier reviews certification evidence packages by subsystem. Local passes identify every required test, but a dependency defect appears only when a controller revision references a sensor test performed against an older interface. The team wants decomposition because the complete package overwhelms one prompt. Which design best preserves local review depth while detecting these cross-package compatibility issues before the release board receives its recommendation?

  1. Correct. Extract versioned requirements and interface references locally, then run a cross-package dependency check before synthesizing the release recommendation.

    Structured local findings preserve detail while an explicit dependency pass tests relationships that cannot be judged within one isolated package.

  2. Incorrect. Create one reviewer per document and send only failing local tests to the release board because passing tests need no further analysis.

    A passing local test may reference an incompatible interface revision; excluding it prevents the cross-package comparison the defect requires.

  3. Incorrect. Add more overlap between adjacent document chunks and let the final summarizer infer any version conflicts from the reviewers’ prose.

    Chunk overlap may help local continuity but does not guarantee that distant interface dependencies are represented or systematically checked.

  4. Incorrect. Ask each subsystem reviewer to give an overall pass score and average the scores to obtain a single package readiness recommendation.

    Averages discard the revision references needed to detect compatibility defects and can hide a blocking dependency behind strong local scores.

Decompose by subsystem, but define the synthesis inputs around requirements, versions and dependencies rather than verdicts alone. Cross-package compatibility is its own obligation. A final dependency check can detect a locally valid test attached to the wrong interface without recreating the entire original context.

Q11 · Deadline slack is not a guarantee

Select 1.

A fictional film archive wants cheaper overnight scene summaries. Its processing window runs from midnight until a broadcast handoff at 06:00, and every missing summary requires an expensive editor intervention. The team proposes the Message Batches API because documentation reports that many batches finish quickly. Which recommendation best connects cost savings to the actual deadline and acknowledges the documented batch processing behavior before the architecture is approved?

  1. Correct. Evaluate batch completion distributions and plan a deadline-aware fallback; typical quick completion does not guarantee success within this six-hour window.

    Batches can take longer or expire, so a six-hour operational deadline requires workload evidence and a defined treatment of unfinished items.

  2. Incorrect. Approve the change because a documented 24-hour processing window guarantees the archive’s batch will finish before its next scheduled handoff.

  4. Incorrect. Compare published token prices alone and select batching if its nominal discount exceeds the editor’s hourly wage expressed in currency units.

    Token discounts and hourly wages use incompatible denominators; the analysis must include unfinished-item probability and the actual intervention cost.

A pricing advantage supports a candidate architecture, not a deadline guarantee. Measure the archive’s workload, track unfinished items against the handoff cutoff and define a tested fallback. The business case must include fallback cost and failure risk as well as nominal batch discounts.

  2. Incorrect. Keep the full patron payload but cache it indefinitely under the patron’s display name so later requests no longer incur any input context cost.

Optimize context around the task’s sufficient information, not the smallest possible payload. A renewal projection can omit unrelated patron details while retaining eligibility, restrictions, identity and version. Those fields preserve the domain invariants that the later action must validate against the current circulation state.
