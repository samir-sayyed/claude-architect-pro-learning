Q1 · Establish the missing review ground truth

Select 1.

A mediation assistant must identify disputed obligations in agreements. Historical files contain final settlements but no obligation labels; reviewers disagree on those labels. The pilot needs evaluation before public use. What BEST establishes feasibility beyond having thousands of documents?

  1. Correct. Agree labels with reviewers and adjudicate a representative sample for a bounded pilot evaluation.

    This addresses missing task ground truth and review consistency, turning an attractive language task into an assessable pilot rather than assuming raw documents prove fit.

  2. Incorrect. Launch with the full corpus; settle labels after public users reveal which answers help.

    Public helpfulness cannot replace the required pre-use evaluation and leaves the unresolved label policy to emerge after users have already relied on outputs.

  3. Incorrect. Derive obligation labels from settlement amounts, treating each completed mediation as evidence of disputed clauses.

    Settlement amounts do not identify disputed clauses or their reasons, so the proposed proxy creates labels that the available records do not actually support.

  4. Incorrect. Compare model tiers by supported agreement length, using corpus capacity as evidence of task feasibility.

    Capacity to accept long text does not establish correct obligation labels or consistent review, which are the missing prerequisites for evaluating this language task.

Resolve the task definition with reviewers and create an adjudicated reference sample before claiming pilot feasibility. The material is language-heavy, but available documents are not automatically usable evaluation evidence. This is a novel application of the chapter’s fit check: uncertainty about labels and review consistency is a prerequisite to investigate, not a reason to treat raw volume as proof.

Q3 · Validate the serialized artifact

Select 1.

A radio gateway requires UTF-8 payloads of at most 240 bytes and an allowlisted incident code. Accented names exceed the byte limit; truncating the code risks misrouting. Retries cost money. One rewrite is allowed before dispatcher takeover. Which design BEST enforces delivery?

  1. Incorrect. Check incoming reports against 240 bytes, then allow unrestricted drafts from inputs that pass.

    Input size does not constrain generated output, and this rejects potentially useful source reports without enforcing the actual delivery boundary.

  2. Correct. Check encoded length and code before sending; allow one rewrite, then escalate remaining failures.

    This checks the actual transport artifact and preserves the code's routing meaning while providing a bounded recovery path for invalid drafts.

  3. Incorrect. Truncate drafts to 240 bytes before sending, retaining the incident-code characters that still fit.

    Truncation enforces size while risking code corruption and meaning loss; the contract requires a valid incident code as well as a bounded payload.

  4. Incorrect. Instruct 240-character drafts and retry rejected deliveries, treating character compliance as sufficient for UTF-8.

    UTF-8 characters can occupy multiple bytes, so this instruction misses the demonstrated failure and charged retries cannot repair an invalid payload.

Validate the exact serialized output at the last pre-delivery boundary. Byte length differs from character count, and the code has routing semantics that truncation can corrupt. A bounded rewrite followed by the same validation preserves useful generation while preventing an invalid artifact from reaching the gateway.
