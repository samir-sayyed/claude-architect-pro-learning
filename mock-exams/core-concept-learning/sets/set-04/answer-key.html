Q1 · Establish the missing review ground truth

Select 1.

A mediation service proposes an assistant to identify disputed obligations in long narrative agreements. The language-heavy task is promising, but historical files contain only final settlements, not explanations of which obligations were disputed. Reviewers disagree about the intended labels, and the pilot must be evaluated before any public use. The sponsor says access to thousands of agreements already proves feasibility. Which next step BEST applies the fit check to the missing evidence rather than treating corpus volume as sufficient justification to build?

  1. Correct. Agree what constitutes a disputed obligation with reviewers, adjudicate a representative sample, and use that reference to define a bounded pilot evaluation.

    This addresses missing task ground truth and review consistency, turning an attractive language task into an assessable pilot rather than assuming raw documents prove fit.

  2. Incorrect. Start the public assistant with the entire corpus and ask reviewers to agree on labels only after users establish which outputs seem helpful.

    Public helpfulness cannot replace the required pre-use evaluation and leaves the unresolved label policy to emerge after users have already relied on outputs.

  3. Incorrect. Use final settlement amounts as automatic obligation labels, because every completed mediation implicitly identifies which narrative clauses caused the dispute.

    Settlement amounts do not identify disputed clauses or their reasons, so the proposed proxy creates labels that the available records do not actually support.

  4. Incorrect. Compare model tiers on agreement length alone, choosing the model that accepts the most files as evidence that the obligation-identification task is feasible.

    Capacity to accept long text does not establish correct obligation labels or consistent review, which are the missing prerequisites for evaluating this language task.

Resolve the task definition with reviewers and create an adjudicated reference sample before claiming pilot feasibility. The material is language-heavy, but available documents are not automatically usable evaluation evidence. This is a novel application of the chapter’s fit check: uncertainty about labels and review consistency is a prerequisite to investigate, not a reason to treat raw volume as proof.

Q2 · Requirements before topology

Which TWO decisions most directly establish measurable non-functional constraints on either proposed topology?

  1. Correct. Identify permitted processing locations and transfers for restricted work orders, with an owner responsible for confirming route eligibility.

  2. Correct. Agree a start-to-usable-briefing deadline under a specified shift-change load, including how incomplete briefings count against the target.

    A deadline tied to a workload and outcome gives both candidate topologies an observable timing acceptance criterion rather than an architectural preference.

  3. Incorrect. Choose the maximum number of specialists now and treat that number as the latency requirement for the shift briefing service.

  5. Incorrect. Require each briefing to sound decisive and polished, replacing the existing rubric with unanimous subjective approval from the architecture team.

    This discards an existing quality contract and supplies neither a measurable timing requirement nor a defined data-processing boundary.

Agree observable timing and data-processing boundaries before choosing a topology. These constrain any model, orchestration, and deployment route. Q3 · Validate the serialized artifact

Select 1.

A field radio gateway accepts UTF-8 payloads of at most 240 bytes and an allowlisted incident code. A drafting assistant usually produces correct incident summaries, but accented place names make some messages exceed the byte limit despite staying below 240 characters. Transport retries are charged, and a truncated incident code can route a message incorrectly. The owner allows one bounded rewrite before a dispatcher takes over. Which architecture BEST enforces the actual delivery contract?

  1. Incorrect. Validate incoming reports against 240 bytes and let the model produce unrestricted output because all admitted inputs already satisfy the channel limit.

    Input size does not constrain generated output, and this rejects potentially useful source reports without enforcing the actual delivery boundary.

  2. Correct. Validate encoded byte length and the incident code before sending; request one rewrite if invalid, then escalate any remaining failure.

    This checks the actual transport artifact and preserves the code's routing meaning while providing a bounded recovery path for invalid drafts.

  3. Incorrect. Apply byte truncation immediately before transmission, retaining whatever incident-code characters remain after the message reaches the gateway limit.

    Truncation enforces size while risking code corruption and meaning loss; the contract requires a valid incident code as well as a bounded payload.

  4. Incorrect. Set a 240-character instruction and retry the gateway automatically, assuming character compliance implies byte compliance for all supported languages.

    UTF-8 characters can occupy multiple bytes, so this instruction misses the demonstrated failure and charged retries cannot repair an invalid payload.

Validate the exact serialized output at the last pre-delivery boundary. Byte length differs from character count, and the code has routing semantics that truncation can corrupt. A bounded rewrite followed by the same validation preserves useful generation while preventing an invalid artifact from reaching the gateway.

Q4 · Refresh the field that changed

Which change BEST repairs the context-assembly defect rather than only altering the wording of an unsupported answer?

    The stale field is availability, so its live authority must supply the context; a later reservation boundary remains necessary as inventory can change.

  2. Incorrect. Refresh the seating catalogue on every request and retain yesterday's availability snapshot, because current seat descriptions establish the seats' present sale status.

    The catalogue and inventory have distinct authority, so refreshing descriptions cannot establish whether another buyer currently holds the suggested seats.

  4. Incorrect. Ask the output validator to reject references to sold seats using only the static seating catalogue, leaving the inventory lookup outside the request path.

    A validator cannot infer live inventory from a catalogue that lacks that field; it needs authoritative current state rather than another processing stage.

The model can explain the observed options, but the final purchase still needs its separate reservation check because suggestions are not a guarantee of later availability.
