01 / UNDERSTAND

Five ideas worth keeping.

Use a protocol because the integration needs it.

MCP offers a common interface and capability discovery across clients. A direct API or CLI may be sufficient for one known integration. A specialist that exercises its own judgment is a different architectural choice from wrapping a tool endpoint.

↗ Lesson 45:00

Delegated identity should not silently become administrator access.

The lesson’s valet-key analogy highlights scoped access: a service must act within the caller’s authority. A broadly privileged shared credential can turn the server into a confused deputy that accesses another customer’s data.

↗ Lesson 54:00

Token handling belongs at a trust boundary.

Validate intended audience and scope; avoid blindly passing an incoming token to another service. Prefer credentials appropriate to the downstream action, keep secrets out of prompts, and enforce resource checks server-side. Tool descriptions cannot enforce those controls.

↗ Lesson 57:00

Capability bloat has four taxes.

Unnecessary tools increase selection ambiguity, token load, security exposure, and audit work. Audit usage, role fit, blast radius, privilege, and overlap. A capability outside the role should be removed, moved, or downscoped rather than merely surrounded with more warnings.

↗ Lesson 79:00

Deferred discovery solves context load, not excess authority.

A large catalog may be legitimate if all tools serve the role. On-demand discovery can reduce the material loaded upfront. An unused destructive tool is a different problem: deferring its description still leaves the capability reachable.

↗ Lesson 86:00
02 / DECIDE

Make the tradeoff visible.

Keep breadth and privilege separate

SituationUseful responseWhy
Unused refund/delete tools in supportRemove or move to the correct roleThe role should not hold that power
Many legitimate, occasionally used toolsEvaluate deferred discoveryReduces upfront context
Read-only job has write credentialsDownscope credentials and enforce checksVisibility alone is insufficient
Transient tool failureTyped error and bounded retryDifferent from a permission denial

Audit each capability

  1. Is it used?
  2. Does it fit this role?
  3. What is the blast radius?
  4. Can privilege be narrowed?
  5. Does another tool overlap?
  6. Keep, remove, move, or downscope

03 / WORKED EXAMPLE · FROM THE LESSON

A support role carries refund and deletion powers

The retail example gives a support agent 14 tools. Refund issuance and account deletion are unused and belong to separate finance and privacy workflows.

THE TEMPTING MOVE

Keep both tools and add logging, confirmation prompts, or deferred loading.

THE BETTER-FITTING MOVE

Remove them from the support role and enforce the appropriate permissions on the server. Keep any required handoff to the responsible workflow explicit.

An audit trail records misuse after the fact. It does not justify granting an unrelated capability.

DETAIL 01

Separate connection, identity, and authority

Choose how systems connect, establish whom the request represents, and enforce what that identity may do. The deck favors MCP for a shared capability across several clients, a direct API for a narrow integration, a CLI where a mature shell interface fits, and an agent handoff when independent judgment is part of the task. A step that always runs can simply be application code.

DETAIL 02

A tool call crosses several permission boundaries

A shared administrator credential can turn an ordinary user request into an unauthorized privileged action: the confused-deputy problem. Validate the user, action, and resource at the server, constrain the backing credential, and expose only the tools the role needs. Keep secrets out of model context. Token audience and downstream credentials need explicit checks; verify current protocol requirements before implementation.

  1. Tool configuration: is this capability part of the role?
  2. Credential scope: can the backing identity do more than the job requires?
  3. Server authorization: may this user perform this action on this resource?
  4. For consequential authorized work: enforce the required human approval.

DETAIL 03

Audit capabilities using five questions

The support scenario has unused refund and account-deletion tools. Remove them from that role when they are not part of its job, and route legitimate work to the owner workflow. Logging or a prompt warning does not reduce the credential’s authority. Lack of recent use is evidence to investigate; an emergency capability may still be justified by an explicit role.

DETAIL 04

Distinguish a broad useful catalog from bloat

The 120-tool IT-operations scenario says the tools are genuinely used, while each request needs only a few. Discovery can reduce context load when extra lookup latency is acceptable and descriptions make capabilities findable. It does not revoke access. The unused support delete button is a different problem: remove authority rather than merely hiding its description until discovery.
